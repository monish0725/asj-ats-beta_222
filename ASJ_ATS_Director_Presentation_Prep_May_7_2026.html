3. Software Flow in Simple Terms

The main flow is:

  1. A resume enters the system through the Website Resume Inbox, manual upload, text submission, or bulk folder import.
  2. The backend stores the original resume in data/uploads and creates an inbox record in data/db.json.
  3. The backend extracts text from the resume using local parsers and fallback logic.
  4. The system checks whether the extracted text is good, partial, or poor.
  5. Readable resumes can be parsed and imported into candidate profiles.
  6. The system extracts skills, role category, experience, seniority, contact details, and summary.
  7. The candidate is matched against open jobs using a scoring function.
  8. Applications are created for the best job matches.
  9. The recruiter manages the application through Applied, Screening, Interview, Offer, and Hired stages.
  10. Talent Intelligence reads the current ATS data and produces recruiter briefs and next actions.

7. Resume Parsing Logic

The resume parser is designed as a dependency-light prototype. The flow is:

  1. Accept only PDF, DOC, and DOCX files.
  2. Reject files larger than 10MB.
  3. Store the file safely using a sanitized filename.
  4. Try local extraction tools first:
    • PDF: pdftotext if available, then macOS metadata fallback.
    • DOC/DOCX: macOS textutil if available.
  5. If local tools are not enough, use built-in fallback logic:
    • DOCX XML extraction from zipped document structure.
    • PDF stream/operator text extraction.
    • Readable text extraction fallback.
  6. Clean the extracted text by removing bad characters and normalizing spaces/newlines.
  7. Score extraction quality as good, partial, or poor.
  8. If extraction is poor, the resume is marked for review instead of creating unreliable candidate data.

8. Candidate Parsing Logic

After resume text is available, the system extracts candidate fields:

  • Email using regex.
  • Phone number using pattern matching.
  • Experience years from text like "5 years".
  • Name from the first useful line before contact information.
  • Skills by comparing resume text against the known skills list.
  • Role category using keyword groups such as AI/ML, Data, Full Stack, Cloud/DevOps, Design, and Backend.
  • Seniority from experience years: Emerging, Mid-level, Senior, or Lead.
  • AI summary and market fit using Cohere when configured, otherwise local summary logic.

9. Matching Engine Logic

The matching engine compares each candidate to each open job. The score includes:

  • Skill match: Required job skills matched against candidate skills. This is the largest part of the score.
  • Experience bonus: More years of experience increases the score up to a limit.
  • Role category bonus: If the candidate role category aligns with the job title/description, the score improves.
  • Eligible role bonus: If AI/local parsing identifies the candidate as eligible for a similar role, score improves.
  • Recommendation label: Score is mapped to top candidate, eligible, possible fit, or not recommended.

Recommendation thresholds:

Score Range Recommendation
85 and above Top candidate
70 to 84 Eligible
55 to 69 Possible fit
Below 55 Not recommended

10. AI / Talent Intelligence Explanation

The AI is not used as a standalone chat window. It is connected to ATS context. The backend sends AI a compact snapshot of:

  • Open jobs and required skills.
  • Candidate names, roles, and skills.
  • Applications, pipeline stages, match scores, and skill gaps.
  • Precomputed recommendations from the matching engine.

We also changed the system prompt so the AI behaves like ASJ Talent Intelligence. It is instructed to write concise internal recruiter briefs with sections like Recruiter Brief, Strongest Matches, Coverage Risks, and Next Actions. The frontend then renders the output as readable sections instead of raw markdown.

12. How to Explain "Built From Scratch"

We built this as a custom prototype rather than installing a ready-made ATS. The frontend is plain HTML, CSS, and JavaScript, and the backend is a Node.js server using built-in modules. The database is a local JSON file for prototype speed, and uploaded resumes are stored in a local uploads folder. This allowed us to build the end-to-end flow quickly without depending on a full database setup.

Even though this is a prototype, the architecture is close to how a production system would be organized: frontend screens, backend APIs, database records, file storage, resume parsing, matching logic, and AI services. For production, we would replace JSON with PostgreSQL, local files with cloud object storage, and basic parsing with a dedicated document parser or OCR service.

16. Questions the Director May Ask

Question Suggested Answer
Is this production ready? This is a functional prototype. The workflow is complete, but production would need authentication, PostgreSQL, secure file storage, OCR/document parser integration, deployment hardening, and permission controls.
Where is the data stored? For the prototype, structured data is stored in data/db.json, and uploaded resumes are stored in data/uploads. In production, this should move to PostgreSQL and object storage.
How does matching work? The system compares job required skills with candidate skills, adds experience and role-fit bonuses, calculates a score, identifies skill gaps, and assigns a recommendation label.
What happens if AI is unavailable? The app still works using local parsing and recommendation logic. AI improves summaries and briefs, but the core ATS flow does not completely depend on AI.
How is this better than a chatbot? The AI is grounded in ATS data. It receives jobs, candidates, applications, scores, and gaps, then returns recruiter-specific decision briefs such as shortlist, interview plan, and coverage risks.
What is the next improvement? The highest-value next steps are website form integration, login/authentication, PostgreSQL migration, OCR parsing, email/calendar actions, and making AI brief actions clickable.
